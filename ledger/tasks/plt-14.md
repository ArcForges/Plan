## Reviewer notes and exact limits

- A caller that cancels while the stream is still opening is reported with effect `Unknown`, not `DidNotHappen`: the HTTP stack reports a plain cancellation that no longer carries the connect marker. This is conservative and was observed, not designed; a stream that fails to open, or whose connect times out, is correctly `DidNotHappen`.
- `CancelAsync` takes no launch and trusts the report the owner's delegate returns; the shipped helper answers `Unknown` for an id it never saw, so it is safe as shipped, but the owner must send the cancel to the launch the command went to. A cancel that reaches the helper before the command leaves no record, so the command can still run and be reported `Happened` (review F2).
- A command that fails before its commit point stays `DidNotHappen` in the helper's table for its retention (10 minutes); a fresh run needs a new command id (review F3).
- A disconnect does not stop a helper-side effect (it runs under a token the call does not own); only an explicit cancel, the effect timeout (30 s) or shutdown does. The replay window (5 minutes) is shorter than the helper's retention (10 minutes) by configuration, not by enforcement.
- The client-side journal, the helper table and the owner store in the tests are in memory (or files in the checks); durable receipts and exactly-once across a parent or helper restart belong to WP07/21/52.
