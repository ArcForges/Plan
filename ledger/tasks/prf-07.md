**Defects found live and their fixes.**
1. *R2 mismatch rejection (run 1; fixed by PR 38).* Mismatching bytes to an existing key were answered 200 `existing`. The cause is inferred from the code and was not observed directly: the conditional write (`etagDoesNotMatch "*"`) returns without R2 evaluating its checksum when the key exists. The offline fake already modelled that order but the only offline mismatch test used a fresh key. Decision: bytes not matching the declared hash must be refused whether or not the key exists (task text: a bounded signed PUT with a server-verified SHA-256); the facade now verifies length and hash itself before any write. Run 2 and later: PUT 201, whole GET 200, range GET 206, mismatching PUT 422 to both the existing and a fresh key.
2. *Egress criterion (run 3; fixed by PR 40).* With Internet access disabled the platform does not refuse connections: the hostname `example.com` timed out after the whole window (8,002 ms) and the literal address `1.1.1.1` was accepted and dropped within about 1 ms (`reached_then_failed`), while the allowed control path (private storage through the interception) answered in the same call and no HTTP response came back for either. The strict criterion of PR 39 could not pass here. **The criterion was amended explicitly (not reclassified quietly) to: pass iff no HTTP response (no status line of any code, including a 520 from a proxy) came back for any attempt, a hostname and a literal address were both attempted, and the control answered in the same call.** Stated limits: it proves the absence of an answer, not the mechanism; a timeout is not required to use the whole window, so a very slow open route could pass; a non-HTTP answer (a banner or a TLS alert) also counts as no response; and the platform's own accept-then-drop behavior is the reason an accepted-then-closed connection counts as blocked here. Tests exercise the real HTTP stack against a closed port, silent listeners, accept-then-close and accept-then-reset peers, answering servers with status 200, 404 and 520 (all fail) and a failed control. Run 4b: `egress-blocked` PASS with `example.com` timeout 8,006 ms and `1.1.1.1` `reached_then_failed` 1 ms.
3. *Rollout lag and provisioning (runs 3 and 4a; mitigated by PR 40, limit remains).* The first operation after a deployment got 404 from an old host instance (run 3), and after the fourth deployment the first foundation calls returned 503 with the platform text "There is no Container instance available at this time ... currently provisioning" for the whole wait (run 4a, started 43 seconds after the deploy finished); the deployment and the instance became usable roughly six minutes after the deploy.
