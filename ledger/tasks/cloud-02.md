## Untested coverage and stated limits

- **The 19 module projects are classed `Abstractions`**, so the shared engine's AT-01 and AT-13 (domain and application dependency rules, module-to-module API rule) do not apply to them. The compensating controls are the Cloud boundary tests above (reference graph, assembly references, namespace scan, layering checker, no-SQL and ownership checks). The layering checker reads type signatures only, not method bodies. A test that fails when a module project gains Domain, Application or Infrastructure namespaces while still classed `Abstractions` does not exist yet; it belongs in the first module task (COM.05, which must also re-review the Entitlement role) and was not added here.
- **No module owns a plan or a table yet.** The checks prove the boundary and the ownership rule on fixtures and the foundation plans, not a module implementation. The physical manifest (CLOUD.03), receipts and outbox (CLOUD.04), the shared families (CLOUD.06) and every module's behavior are later tasks. The typed repository API for modules does not exist yet; the bridge is internal to the host and `Storage.D1`.

SQLite is not D1: the offline vectors prove SQL, constraints and rollback, not the provider's network path.
