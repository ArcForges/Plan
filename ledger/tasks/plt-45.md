## Untested coverage (stated expressly)

- **Nothing was run on Linux.** The Linux launcher and profile were compiled in hosted CI and unit-tested only (the seccomp program is run by an offline interpreter; Landlock and the spawn plan are checked as data). `wsl.exe` was excluded. Whether a Linux kernel enforces the profile, including the Landlock multithread flag (which makes the profile unavailable on a kernel without it), the memfd seals and the close-from action, is unobserved. No offline test observes the Landlock TSYNC flag or the shrink seal: a mutant that drops either survives offline.
- **Why `delivered` and not `complete`, in full:** NAT.14 is open, and in addition the task's own evidence requires OS denial and parent-death cleanup on every supported RID. That is observed on Windows only: Linux was never run and macOS has no launcher. Completing PLT.45 therefore needs NAT.14 and the missing Linux and macOS observations (or a recorded planning decision that narrows the supported RIDs).
- **macOS has no launcher**; entitlements are data only; no XPC activation shim and no signed sandboxed bundle.
- **No Authenticode verification** of the helper (the launcher pins a SHA-256 only); no Windows ARM64 or other RIDs; no per-RID Runtime packages (PLT.46).
- **No LPAC opt-out**: the AppContainer keeps the default ALL APPLICATION PACKAGES read access to system locations. Dynamic-code and win32k mitigations were tried and are **not** enabled (win32k and the child-process policy broke start-up under the console host; dynamic-code prohibition is untested with real parsers).
- **Real PDF and image parsers are not composed**, so containment against production libraries and hostile real-format inputs is unproven; the attacks use only a hostile first-party fixture. The full PG-22 closure remains with NAT.14, PLT.54 and WP41.
- **AppContainer storage reuse is unproven**: pooled identities are reused one after another and keep their per-container storage between invocations; nothing cleans it on release and no test covers it.
- **Linux gaps even if the profile ran**: `tgkill` to another process of the same user stays possible (the runtime needs it); there is no PID, user or mount namespace; there is no kill-on-close, so a wedged helper whose parent was killed is not ended by the kernel (parent loss is the helper's poll of its parent id, and no parent-death signal is used because it is bound to the spawning thread); on Linux a rename in the install directory between hash and start is not blocked (advisory share mode), so the install directory must be unwritable for the user.
- **Windows exit codes after termination reflect the parent's own kill**, and the Windows parent-lost, hang and memory-exhaustion results were observed on one machine and one OS build.
- **Same-account caveat**: the claimant commits, PRs, and every review or approval comment (including those cited as independent) were made from the same GitHub account; independence is by distinct worker and reviewer identity only.
- No macOS, hosted GUI, device, live-service, real-inference or installed-consumer validation is claimed.
