## Completion follow-up (2026-10-05, epoch 1 of claims/plt-48, worker w-c20261005-plt48f): status stays `delivered`

CLOUD.01 is `complete` ([ledger record](cloud-01.md), Cloud [PR 42](https://github.com/ArcForges/Cloud/pull/42) merged as `7c606cda27bfb4e85f7cb39110a4bb1039d8d466`), so `ready` listed PLT.48 as a completion follow-up. This follow-up read the PLT.48 task prompt, WP-12.01 and its completion gate, architecture 13 (CR-01 to CR-06, HP-06), the CLOUD.01 record and `docs/cloud-ingress.md`, and the Cloud and DesktopPlatform sources at the commits named below, to decide what the task's own remaining acceptance needs. Nothing was run against the deployed proof environment, no code was changed and no pull request other than this record was opened. The result is that the acceptance cannot be met by an observation, and that it cannot be met by a minimal change either; this record states exactly why, so that nothing is claimed that was not observed.

What the acceptance asks for. The task prompt and WP-12.01 require "one synthetic action produces one connected trace across every hop kind" (HTTP, queue, worker, realtime and provider), with the task's completion prerequisite naming "a real Cloud hop to prove the full HTTP/queue/worker/realtime/provider chain". Architecture 13 CR-01 and CR-06 ask for one correlation identity across API, queue, worker, task runner, realtime and outbound provider calls, and HP-06 asks for every Cloud response to carry the correlation identity.

Findings (source reading only; Cloud at `7c606cd`, DesktopPlatform at `5405d80`; no deployed check):

- **The deployed Cloud ingress does not carry correlation in either direction.** A search of every file tracked in Cloud finds no code, and no Worker, host or documentation text, that reads, validates, propagates, echoes or logs a correlation identifier or a W3C `traceparent`: the only matches are five operational runbooks (prose) and one host test that sets `RequestMeta.CorrelationId` as an input the pipeline then ignores (`IngressPipelineTests.cs`). `RequestEnvelopeReader` reads only the workspace and recovery generation of `RequestMeta`; the proof probe's replies carry no `ResponseMeta` or correlation; the anonymous Hello contract has no request or response meta at all. The statement in the CLOUD.01 record that "the correlation propagation across it is PLT.48's own follow-up" is therefore not a check that can be run: there is nothing on the Cloud side to observe, and PLT.48's write scope (`ArcForges.Observability/**`) cannot supply it.
- **PLT.48 has no wire or client component.** By design (the delivered record: "no custom header or string grammar was introduced") `CorrelationPropagation.BeginOrigin` accepts a validated typed client value (`Id`, the `RequestMeta.correlationId` of wire registry 04) and the local hops are in-process calls; `ArcForges.Observability` contains no HTTP or gRPC client and no code that writes a correlation identifier onto a request. A local run could therefore only prove what PLT.53's consumer run already proved (the in-process chain), plus an uninstrumented call to Cloud that cannot show the identifier arriving.
- **Three of the five hop kinds have no real Cloud implementation to join.** The Worker has a wake Queue and its consumer (job wake and dead-letter probe, proof-only retry scenarios) whose messages carry no correlation; Cloud contains no realtime, WebSocket or stream-service code (CLOUD.29 and CLOUD.34) and no outbound provider code (egress is blocked by design in the proof environment; AI and provider owners are other tasks). The only real hops are the HTTP ingress (Worker to host) and the proof-only probe stream.
- **No Cloud task owns correlation.** A search of the Plan `tasks/cloud.md` and `tasks/operations.md` prompts for correlation finds none; WP-21.00 has no correlation obligation. Making the ingress read `RequestMeta.correlationId` (field 3), validate it as a canonical UUID, expose it on `CallerContext`, put it on `ResponseMeta` and `ArcError` and carry it to queue messages would be new behavior in a delivered, production-deployed pipeline (the main-push run deploys it to production), needs a planning decision on its owner and scope, a reviewed Design and Plan pair, a Cloud pull request, a proof deployment under the lease `RES-cloud-deployment` and a live run, and a C# client in DesktopPlatform to originate the call. Even if all of that were done, the realtime and provider hops would still not exist, so the "every hop kind" gate could not be met and PLT.48 would still not be `complete`. The cost and the production risk of that slice buy no change of the task's state, so it was not started.

Conclusion and decision. PLT.48 stays `delivered`. This follow-up does not claim a Cloud hop, a connected cross-owner trace or any live observation. No local opt-in run was made against `https://proof.arcforges.com`, because no run could show correlation arriving at or leaving Cloud; the lease `RES-cloud-deployment` was not taken; production, `workers.dev` and every credential were untouched.
