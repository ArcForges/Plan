## Untested coverage and known limits

- **Every egress port is a fake.** No real classifier (so no claim that content is labelled correctly), allowlist or grant store (so no claim that a grant reflects the user's consent), and no audit adapter: the audit store is a separate project Security does not reference (PLT.44), and a late `Authorized` record beside a refusal is possible there.
- **No socket interception.** An owner operation that takes the `AuthorizedEgress` ticket cannot be called without a decision, but code that opens a connection by itself is not stopped. DNS resolution, address pinning and redirect handling belong to the sender (APP.06 and other senders); name-based identity says nothing about which address answers.
- **No product attachment.** The authority is not wired into any product's invocation pipeline (PLT.57) or into the context and artifact integration (APP.06), and no cross-process call exists.
- **Pipeline step 8 stays a verdict.** The specific egress reason is only in the egress audit record, not in the pipeline's own decision.
- **Not an input:** effective risk (the pipeline already raises it for an external destination and automation), grant origin or device constraints, and remote-origin handling beyond the pipeline's own steps.
- **Same-account review.** The independent review ran in a separate session, but its comments come from the same GitHub account as the claim.
- No macOS, hosted runtime, device, GUI, browser E2E, live-service, inference or installed-consumer validation was performed and no Native AOT publish of the changed project ran locally. The local `ArchitectureTests` run fails only on the existing `Security.Secrets` CS8795 reconstruction gap (recorded by PLT.37, PLT.38 and PLT.39), so RP-10 was judged by the hosted gate.
