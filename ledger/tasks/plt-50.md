## Limits and untested coverage

- **Values left to deployment.** `sampling.head.defaultRatio`, `sampling.promotion.slowSpanThresholdMs` and `retention.durationsByClassAndEnvironment` remain `null` under `notFixedByDesign`: Design fixes none of them. The first two are required `TracePolicyOptions` constructor arguments with no library default (a test asserts this). Retention durations at a telemetry backend are not modelled by the library; the only retention it enforces is the in-process 30 second trace window. They are owned by deployment configuration, PLT.53 and the operations telemetry adapter work (WP-45), not by PLT.50.
- **Installed in no pipeline.** The repository has no exporter or OpenTelemetry dependency; `TracePolicy` and the label policy are used by no host, and the sinks in the tests are test doubles. Wiring is PLT.53 and the product hosts.
- **Offline evidence only.** No live telemetry backend, hosted device, GUI, browser or installed-consumer validation was performed (outside P2-017). No macOS runtime or artifact was produced or observed; Linux evidence is the hosted compile, AOT and test runs above.
- **Buffer cost is an accounting model**, a deterministic charge per span, entry, promotion state and closed-trace marker, not a measurement of process memory. The 30 second window is logical and lazy: it is applied when a span arrives or statistics or instruments are read, with no timer, so on an idle process held spans stay in memory (within the budget, never exported) until the next call.
- **Consent caveats.** `ITelemetryConsent` has no change notification, so revocation is applied when the next span ends, when an instrument is read while consent is absent, or when the host calls `PurgeBuffer`. PLT.52 must call `PurgeBuffer` at revocation; without it, spans collected before a revocation and re-grant with nothing observed in between could be exported afterwards (pinned by a test that documents the gap). With consent absent the attached listener keeps recording spans and keeps setting the head-sampled flag that propagates on outgoing context; only export, holding, error facts and instrument measurements stop. `SignalEmitter`'s own sink and instruments are not consent-gated by this task.
- **Sampling and export caveats.** Promotion export is not rate-capped: the bound is on the buffer, not on what an error storm exports. The head sampler trusts a remote parent's sampled flag, so a caller that sends a sampled trace context forces recording and export regardless of the ratio; a Cloud ingress host decides whether to honour it. Sinks are called concurrently from arbitrary threads and must be thread-safe (documented on both sink interfaces).
- **Error counter and the log sink.** The error counter increment follows the event write, so when the structured event sink throws, that error's `arcf_span_error_count` increment is lost along with its event; the failure is visible only in `ExportFailures` and `ErrorFacts` does not count it. This is documented on `ErrorFacts` and pinned by a test. The README sentence that every error span records one event and one increment holds only while the log sink works.
- **Per-error-span retention is not guaranteed.** A late error span (its trace's window closed) is not exported and is counted in `ErrorSpansNotRetained`; its error fact is still recorded. This is the designed absence of an all-errors trace retention guarantee.
